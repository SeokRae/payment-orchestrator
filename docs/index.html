결제/PG 서비스 출시를
10명의 AI 에이전트 팀이 준비합니다

기획부터 규제 준수 심층 검토, 논리·물리 아키텍처 설계, 트랜잭션 세션 설계, 운영 전략, 인터페이스 스펙, 점진적 QA, 구축 보고서까지 — 신규 결제/PG(Payment Gateway, 결제대행사) 서비스 출시에 필요한 설계 문서 세트를 한 번에 만드는 Claude Code 하네스입니다.

QA 게이트는 아키텍처 설계 이후 5개 체크포인트에 적용되며, 그 앞의 기획·규제 심층 검토 단계에는 별도 게이트가 없습니다.

GitHub 저장소 사용법 바로가기 전체 README

시작 전에 알아두면 좋은 것

전체 팀을 스폰하기 전에 이 4가지는 꼭 확인하세요.

설계 문서만 만듭니다

실제 코드 구현과 그 코드가 스펙대로 동작하는지 확인하는 "개발 QA"는 범위 밖입니다. 산출물은 완성본이 아니라 (미결)·(미확인)·(미확보) 표기가 남은 초안이며, 사람의 최종 확인이 필요합니다.

규제 체크리스트는 한국 법제 기준

전자금융거래법·특정금융정보법 등 리서치 시점의 한국 법제를 근거로 합니다. 해외 연동 시나리오도 다루지만 판단 근거 법령 자체는 한국 기준입니다.

처음 실행할 땐 가볍지 않습니다

신규 서비스로 트리거하면 10명 전원이 곧바로 스폰되는 전체 파이프라인이 실행됩니다. 정상 흐름 기준 에이전트 호출 약 22~24회, 수십 분~여러 시간 규모입니다. 가볍게 확인하려면 compliance-review·qa-review를 단독 트리거하세요. 이미 만든 서비스의 후속 요청(예: "제약분석만 다시")은 팀원 1명만 재소집되므로 예외입니다.

확인 질문은 최대 3번

시작 직후 역인터뷰, 아키텍처가 갈릴 때 옵션 선택, 보고서 확정 전 핵심 결정 확인 — 모두 게이트가 아닌 선택적 보강이라 응답하지 않아도 기본값으로 자동 진행됩니다.

파이프라인 한눈에 보기

스킬 3개

compliance-review·qa-review는 팀 전체를 돌리지 않고 단독으로도 쓸 수 있습니다 — 오케스트레이터 안에서 각각 compliance·qa 팀원이 내부적으로 호출하는 것과 동일한 스킬입니다.

launch-orchestrator

"신규 결제 서비스 출시", "PG 서비스 구축 하네스"

팀 전체를 조율하는 메인 스킬 — 10명 스폰, 착수 게이트 G1~G5 관리, 부분 재실행(특정 팀원만 재작업) 처리.

오케스트레이터

compliance-review

"규제 검토", "PG 등록 대상인지 확인"

전자금융거래법·PCI-DSS·개인정보보호법·특정금융정보법(특금법)·해외 PSP 연동(외국환거래법·GDPR) 5개 규제 도메인을 77개 체크리스트 항목으로 H/M/L 등급 판정. 법률 자문이 아닙니다.

단독 트리거 가능

qa-review

"설계 문서 정합성 검증", "QA 해줘"

설계 문서 간 경계면 교차검증(PASS/FIX/GAP 판정). "문서 QA"만 다루며, 코드가 스펙대로 동작하는지 확인하는 "개발 QA"는 범위 밖입니다.

단독 트리거 가능

사용법

  1. 설치 — 상황에 맞게 고르세요.
    • 플러그인으로 설치 (여러 프로젝트에서 재사용할 계획이면 권장): 플러그인 이름은 payments이며, 설치되면 스킬은 payments:launch-orchestrator 형태로 노출됩니다. 
      claude plugin marketplace add <이 저장소 경로 또는 git URL>
claude plugin install payments@sr
      또는 등록 없이 바로 로드: claude --plugin-dir <이 저장소 경로>
    • 디렉터리 복사 (지금 이 프로젝트 하나에서만 빠르게 써보려면 더 간단): agents/·skills/ 안의 파일들을 대상 프로젝트의 .claude/agents/·.claude/skills/로 복사합니다.
  2. 세션에 입력합니다. 
    새 결제 서비스 'xyz-pay' 출시 준비 문서 만들어줘 — 해외 카드사 다이렉트 연동, Q3 목표
  3. launch-orchestrator 스킬이 트리거되어 10명 팀이 자동으로 조율하며 작업합니다.
  4. 결과는 {service-root}/docs/{kickoff,constraints,architecture,session-design,operations,specs,adr,reports}/에 생성됩니다. {service-root}는 최초 실행 시 하네스가 직접 물어보며 정합니다.

후속 작업: 이미 만든 서비스에 대해 "제약분석만 다시", "아키텍처 수정해줘" 같은 요청도 같은 스킬이 처리합니다 — 영향받는 팀원만 골라 재실행합니다(전체 팀 재소집 아님).

전제 조건

이 하네스는 문서를 어디에 둘지 특정 폴더 구조를 강제하지 않습니다. 오케스트레이터 Phase 0가 실행 시점에 {service-root}를 프로젝트 컨벤션에서 찾거나, 없으면 사용자에게 직접 물어서 정합니다.

외부 플러그인·노트 앱에 전혀 의존하지 않습니다. Obsidian이 설치돼 있을 필요도, 다른 노트 도구가 있을 필요도 없습니다 — 문서 구조는 표준 폴더와 각 문서 최상단의 # 제목 헤더, 표준 마크다운만으로 자기완결적으로 구성됩니다. 특수 프론트매터 필드나 wiki-link([[...]]) 문법도 쓰지 않습니다.

설계 범위 — "문서 QA"와 "개발 QA"

이 하네스는 설계 문서만 다룹니다. payment-launch-qa가 하는 검증은 "세션설계 시나리오가 스펙에 API로 다 옮겨졌나" 같은 문서 대 문서 정합성이며, 실제로 구현된 코드가 그 스펙대로 동작하는지는 확인하지 않습니다. 코드는 이 저장소 밖의 별도 코드베이스에 있고, 그건 별도의 개발+QA 하네스가 필요한 영역입니다. payment-ops-designer가 만드는 "테스트 전략" 문서가 그 다음 단계(개발 QA)로 넘어가는 핸드오프 산출물 역할을 합니다.

설계 원칙

  • 생산자와 검증자를 분리한다 — payment-launch-qa는 문서를 만들지 않고 교차검증만 합니다. 스스로 만든 문서를 스스로 검증하면 놓치는 게 그대로 남습니다.
  • 점진적 QA — 전체 완성 후 한 번에 몰아서 검증하지 않고, 각 생산자가 끝나는 즉시 바로 확인합니다. 문제를 일찍 잡을수록 되돌리는 비용이 작습니다.
  • 재시도는 진행이 있는 한 계속한다 — QA 재검증은 고정 횟수 상한이 아니라 무진행 감지로 종료 시점을 정합니다. 더 이상 나아지지 않는 지점에서는 강제 통과 처리 후 미결로 남깁니다. 무한 루프보다 "사람이 확인할 목록"을 남기는 쪽을 택합니다.
  • 역할이 다르면 에이전트를 분리한다 — 인프라 구축(물리·실행형)과 어플리케이션 설계(논리·문서형)는 성격이 다르다는 판단으로 별도 에이전트로 나눴습니다. 규제·정책 판단도 마찬가지로 전문화했습니다.
  • 스킬(어떻게)과 에이전트(누가)를 분리한다 — 규제 판단 로직과 QA 판정 로직은 독립 스킬로 빼서, 팀 밖에서 단독으로도 쓸 수 있게 했습니다.
  • 사용자 확인 왕복은 게이트가 아니다 — 역인터뷰·아키텍처 옵션 제시·핵심 결정 확인 모두 착수 순서를 강제하는 게이트(G1~G5)와는 성격이 다릅니다. 답하지 않아도 기본값으로 자동 진행되어 파이프라인을 막지 않습니다.

에이전트 상세

에이전트는 "누가 하는가"(역할·권한이 고정된 팀원, 스폰되면 독립된 컨텍스트에서 작업), 스킬은 "어떻게 하는가"(여러 호출자가 공유해 꺼내 쓰는 절차서)입니다.

주요 협업
ops와 서버 존 구성 ↔ 운영 전환 일정 상호 확인

8. payment-launch-qa — 설계 문서 정합성 검증
착수 조건
게이트 없음 — architect·infra·session·ops·spec 각 완료 직후 자동 트리거(5개 체크포인트)
핵심 역할
qa-review 스킬로 경계면 교차검증 수행, PASS/FIX/GAP 판정
핵심 원칙
"존재 확인"이 아니라 "교차 비교", 재검증은 무진행(그 항목에 이미 나온 적 있는 지적이 다시 등장하거나 체크포인트 전체가 2라운드 연속 정체) 감지 시 강제 PASS, REDO급 불일치는 판정 없이 즉시 리더 에스컬레이션
입력 → 출력
인접 문서 쌍 → _launch-workspace/qa/{NN}-*.md(docs/에는 쓰지 않음 — 감사 기록)
주요 협업
FIX/GAP 시 해당 생산자에게 직접 통지, 불일치가 미결정 때문이면 결정 확정 책임자(관련 생산자, 애매하면 리더)에게 먼저 확정을 요청한 뒤 adr에게 기록을 요청하고 재검증
원본 파일
agents/payment-launch-qa.md
9. payment-decision-recorder — ADR 기록(adr)
착수 조건
고정 게이트 없음 — 전 팀원 요청에 상시 대기(on-call)
핵심 역할
되돌리기 어려운 결정을 ADR로 구조화, 상태(proposed→accepted/rejected/superseded) 관리
핵심 원칙
"되돌리기 어려운가"만 기록 기준(사소한 선택은 반려), 번호는 순차 증가·재사용 금지, 상충 시 삭제 대신 superseded 처리
입력 → 출력
팀원의 결정 컨텍스트 요청 → docs/adr/adr-{NNN}-*.md
주요 협업
reporter가 보고서 초안 작성 착수 시점에 ADR 전체 목록(상태 포함)을 요청
원본 파일
agents/payment-decision-recorder.md
10. payment-launch-reporter — 구축 보고서 종합
착수 조건
G5 — 인프라·운영·스펙 3개 QA 체크포인트 모두 완결
핵심 역할
전 산출물 + QA 결과 + ADR 이력을 표준 목차(배경/개요/아키텍처요약/로드맵/현황/리스크레지스터/주요의사결정)로 종합. 초안 완성 후 영향이 큰 ADR 1~3개를 사용자에게 되물어 이해도를 확인(사용자 확인 왕복 UC3)하고 필요하면 해설을 보강한 뒤 확정
핵심 원칙
개별 문서 복붙 금지(관점 재구성), 리스크 레지스터는 전 팀원 미결 항목을 누락 없이 통합, "ADR 필요 여부 검토함" 문구와 adr의 실제 목록을 대조해 누락 감지
입력 → 출력
docs/{kickoff..specs,adr}/ + QA 기록 → docs/reports/{service-slug}-플랫폼-구축-보고서.md
주요 협업
팀의 마지막 단계(확정본 기준) — 리더가 이 산출물을 최종 결과로 사용자에게 보고
원본 파일
agents/payment-launch-reporter.md
