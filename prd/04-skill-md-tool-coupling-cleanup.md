# PRD-04: SKILL.md 본문에 남은 툴 종속 서술을 부록 A로 완전 이동

**우선순위:** Low · **작성일:** 2026-08-02 · **예상 규모:** 작음 (`.claude/skills/payment-launch-orchestrator/SKILL.md` 3곳 재서술)

## 배경

이번 사이클의 핵심 변경 중 하나가 "오케스트레이터 실행 계층을 게이트 규범(본문, 툴 비종속)
+ API 매핑(부록 A)으로 분리"였다. 실제로 Phase 2(팀 구성)는 `TeamCreate`/`TaskCreate(depends_on)`
코드블록을 걷어내고 G1~G5 게이트 표(파일 존재 여부 같은 관측 가능한 조건)로 재작성됐고, 파일
끝(209번째 줄)에 "부록 A — 현행 Claude Code API 매핑" 섹션이 신설돼 구체적 툴 이름은 대부분
거기로 옮겨졌다. 부록 A는 "툴 이름·파라미터가 바뀌면 이 부록만 갱신하고, 본문(Phase 2)의
게이트 정의는 건드리지 않는다"는 분리 원칙을 명시한다 — 210번째 줄.

## 문제

이 분리가 Phase 2 안에서는 잘 지켜졌지만, **본문의 다른 세 곳에는 여전히 구체적 툴 이름/호출
구문이 그대로 남아 있다** (2026-08-02, `grep -n "TaskGet\|TaskList\|TaskCreate\|TaskUpdate\|Agent("`로 확인):

| 줄 | 위치 | 내용 |
|---|---|---|
| 48 | Phase 0 (컨텍스트 확인, 부분 재실행 절차) | `Agent(subagent_type: "...", model: "opus", prompt: ...)` 호출 구문이 직접 하드코딩 — 부록 A "1) 팀원 스폰"(213~228번째 줄)과 내용이 사실상 중복 |
| 100 | Phase 3 (실행, 리더 모니터링) | `` `TaskGet`으로 전체 진행률 확인, 특정 팀원이 30분 이상 진행 없이 막히면 `SendMessage`로 상태 확인 `` |
| 121 | Phase 4 (통합 확인) | `` 1. `reporter` 작업(`구축 보고서 종합`) 완료 대기 (`TaskGet`) `` |

(참고: 93번째 줄에도 `TaskList`가 등장하지만, 이는 게이트 절차를 지시하는 문장이 아니라
"on-call 팀원은 고정 태스크가 없어 TaskList로 참여 여부가 보이지 않는다"는 **한계를 설명하는
서술**이라 이 PRD의 필수 수정 대상은 아니다 — 손대도 되지만 우선순위 낮음.)

이 때문에 부록 A 서두의 "본문은 툴 비종속"이라는 선언과 본문의 실제 상태 사이에 잔여 불일치가
있다. 툴 API가 다시 바뀌면(예: `TaskGet`이 다른 이름으로 바뀌면) 부록 A만 고치면 된다는
설계 의도가 이 세 곳에서는 깨진다 — 본문도 같이 고쳐야 한다.

## 목표

Phase 0·3·4에 남은 툴 이름/호출 구문을 제거하고, 부록 A를 참조하는 툴 비종속 서술로
재작성한다. "본문 = 무엇을(게이트), 부록 A = 어떻게(툴 API)"라는 분리를 SKILL.md 전체에
일관 적용한다.

## Non-goals

- 부록 A 자체의 내용 변경 (이미 팀원 스폰·작업 등록·진행률 확인 3개 섹션으로 잘 구성돼 있음
  — 아래 요구사항에서 본문이 참조할 대상으로만 활용)
- Phase 2의 게이트 표(G1~G5) 자체 변경 — 이미 완료된 부분

## 요구사항

1. **48번째 줄 (Phase 0)**: `Agent(subagent_type: ..., model: "opus", prompt: ...)` 하드코딩
   구문을 제거하고, "필요한 팀원만 골라 재소집한다(스폰 방법은 부록 A '1) 팀원 스폰' 참조)"
   같은 문장으로 축약한다. 부록 A의 팀원 스폰 목록(218~227번째 줄)이 이미 10개 팀원 전부를
   커버하므로 중복 정보를 본문에 유지할 이유가 없다.

2. **100번째 줄 (Phase 3)**: `` `TaskGet`으로 전체 진행률 확인 `` 을 "각 태스크의 진행 상태를
   확인한다(방법은 부록 A '3) 진행률 확인·종료' 참조)"로 교체. `SendMessage`는 툴 이름이라기보다
   팀 통신 방식 자체를 가리키는 일반 용어로 이미 본문 전반에서 쓰이고 있어(예: 93번째 줄,
   에러 핸들링 표 전체) 이 부분은 그대로 둔다 — `SendMessage`까지 추상화하면 오히려 본문이
   읽기 어려워진다.

3. **121번째 줄 (Phase 4)**: `` 완료 대기 (`TaskGet`) `` 부분만 제거하고 "`reporter` 작업
   (`구축 보고서 종합`) 완료 대기"로 남긴다 — 굳이 대체 문구를 추가할 필요 없이 괄호 안
   툴 이름만 삭제해도 문장이 자연스럽다.

4. 부록 A "3) 진행률 확인·종료" 섹션(287~291번째 줄)이 본문 100·121번째 줄이 참조할 내용을
   실제로 담고 있는지 확인한다 — 현재 287번째 줄에 `TaskList`/`TaskGet` 사용법이 있어 충분해
   보이지만, "특정 팀원이 30분 이상 막히면 상태 확인"처럼 본문에만 있던 임계값·행동 규칙이
   부록에는 없다는 점도 함께 확인해, 필요하면 그 규칙 자체(30분 임계값)는 본문에 남기고
   "어떤 API로 확인하는가"만 부록을 참조하도록 구분한다 (규칙 vs 구현 수단을 헷갈리지 않는다).

## 완료 기준

- [ ] `grep -n "TaskGet\|TaskList\|TaskCreate\|TaskUpdate\|Agent(" .claude/skills/payment-launch-orchestrator/SKILL.md` 결과에서 209번째 줄(부록 A 시작) 이전 매치가 0건 (93번째 줄의 설명적 `TaskList` 언급은 예외로 허용하거나, 함께 정리해도 무방)
  - `SendMessage`는 이 grep 대상에서 제외(팀 통신 방식을 가리키는 일반 용어로 취급)
- [ ] Phase 0·3·4를 다시 읽었을 때 "무엇을 해야 하는가"는 본문만으로 이해되고, "어떤 API로
      하는가"는 부록 A를 봐야 알 수 있는 구조가 유지됨
- [ ] 부록 A "3) 진행률 확인·종료" 섹션이 본문이 참조하는 내용을 실제로 커버함
