# Payment QA Review — 결제 서비스 설계 문서 정합성 검증

결제 서비스 출시 설계 문서 세트(기획·규제·아키텍처·인프라·세션·운영·스펙)가 개별적으로는 그럴듯해도, **서로 맞물리지 않으면 실제 구현 단계에서 재작업**이 생긴다. 이 스킬은 "문서가 존재하는가"가 아니라 "인접한 두 문서가 실제로 같은 이야기를 하는가"를 확인한다.

## QA의 두 층위 — 반드시 구분한다

| 층위 | 확인 대상 | 이 스킬의 범위 |
|------|----------|--------------|
| **문서 QA** | 설계 문서 A와 B가 서로 정합적인가 (경계면 교차검증) | **범위 안** — 이 스킬의 본체 |
| **개발 QA** | 실제로 짜인 코드가 스펙대로 동작하는가 (테스트 실행) | **범위 밖** — 코드는 별도 코드베이스에 있고, 이 스킬은 설계 문서만 다룬다. 대신 "핸드오프 준비도"(아래 6번)만 확인 |

이 구분을 흐리지 않는다 — "테스트 케이스가 몇 개 있다"는 문서 QA로 확인 가능하지만, "그 테스트가 실제로 통과한다"는 이 스킬로 확인할 수 없는 사실이다.

## 검증 원칙

- **존재 확인이 아니라 교차 비교** — "정산 전략 문서가 있다"가 아니라 "정산 전략 문서가 언급하는 존 구성이 인프라 문서의 실제 존 구성과 같은 이름을 쓰는가"를 확인한다. 두 문서를 동시에 Read해서 구체적 항목 단위로 대조한다
- **PASS / FIX / GAP 3단 판정** — PASS(정합적), FIX(부분 수정으로 해결 가능한 불일치), GAP(한쪽에서 언급조차 안 된 누락). REDO는 없다 — 이미 나온 설계 문서를 통째로 다시 쓸 정도의 불일치는 팀 전체에 영향을 주므로 판정 대신 리더에게 즉시 에스컬레이션한다
- **재검증 종료는 횟수가 아니라 무진행(no-progress) 감지 기준** — "같은 불일치"는 같은 항목(필드·컴포넌트·섹션) 기준으로 판단한다. 값이 바뀌었어도(예: 타임아웃 값이 반대 방향으로 어긋남) 같은 항목이면 동일 불일치로 카운트한다. 재검증에서 지적 사유가 그 항목에 대해 이전에 나온 적 없는 새로운 사유인 한(=진행이 있는 한) 왕복 횟수 제한 없이 계속 재검증한다 — "충분히 구체화됐다"는 판정을 횟수보다 우선한다. 다만 같은 항목에서 **그 항목의 지금까지 재검증 이력 전체 중 이미 한 번 나왔던 것과 동일한 위치·동일 사유**가 다시 등장하면(**직전 라운드가 아니어도 해당** — 예: A→B→A처럼 두 상태를 오가는 오실레이션도 무진행으로 잡는다. 이번 수정이 사실상 그 항목을 순환시키기만 했다는 뜻) 무진행으로 보고 그 항목만 즉시 강제 PASS 처리하고 미결 항목으로 리포터에게 넘긴다. 생산자 수정이 매번 다른 항목을 새로 어긋내(A를 고치다 B를 틀리는 식) 개별 항목은 무진행에 걸리지 않는 경우에 대비해, **체크포인트 전체의 남은 불일치 항목 수를 라운드마다 그 체크포인트의 지금까지 최저 기록과 비교**한다 — 2라운드 연속으로 그 최저 기록을 갱신하지 못하면(늘거나 같은 수준을 오가기만 해도 해당) 체크포인트 전체를 무진행으로 보고 그 시점까지 남은 모든 불일치를 일괄 강제 PASS 처리한다 (무한 루프 방지는 횟수 상한이 아니라 진행 여부 감지로 보장 — 직전 라운드만이 아니라 전체 이력과 비교해 오실레이션도 무진행으로 잡아낸다). 여기서 체크포인트 단위의 "라운드"란 개별 항목 하나의 재검증 이벤트가 아니라 **그 체크포인트에서 아직 열려 있는 FIX/GAP 항목 전체를 한 바퀴 재검증한 것**을 가리킨다 — 생산자가 항목별로 따로따로 수정 완료를 알려오는 비동기 상황에서도, 아직 재검증 기회를 받지 못한 다른 열린 항목이 있으면 그 항목들도 최소 1회 확인해야 라운드가 넘어간 것으로 센다(그렇지 않으면 한 항목만 계속 삐끗하는 동안 아직 손도 못 댄 다른 항목까지 조기에 일괄 강제 PASS될 수 있다)
- **판정 근거는 항상 두 문서의 구체적 위치를 인용** — "정합적이지 않다"가 아니라 "session 문서의 '해외카드 승인' 시나리오 3번째 스텝이 spec 문서 어디에도 API로 없다"처럼 인용 가능한 수준으로 지적한다
- **용어 체계가 달라 비교가 안 되는 경우는 FIX다** — 양쪽 문서에 내용 자체는 있는데 컴포넌트·필드 이름 체계가 서로 달라 대응 여부를 판정할 수 없는 경우, "누락"(GAP)이 아니라 "부분 수정으로 해결 가능한 불일치"(FIX)로 분류한다 — "두 문서 중 어느 쪽 용어로 통일할지"를 생산자에게 SendMessage로 확인

## 검증 매트릭스 (5개 체크포인트)

launch-orchestrator 팀에서는 각 생산자가 완료되는 즉시 해당 행을 수행한다 — 행 번호는 대표 순서일 뿐 실제 실행 순서가 아니다. 2·3·4번은 병렬 팬아웃 구간이라 완료 순서가 보장되지 않고, 6번(부가)은 5번보다 먼저 트리거될 수 있다. 단독 트리거 시에는 사용자가 지정한 두 문서(또는 전체)에 해당하는 행만 골라 수행한다.

| # | 체크포인트 | 비교 대상 | 확인 기준 |
|---|-----------|----------|----------|
| 1 | architect 완료 직후 | compliance의 H급 규제 항목 ↔ architect 컴포넌트 설계 | H급 규제(예: PAN 비저장 강제)가 실제 컴포넌트 구조에 반영됐는가, 조용히 무시된 항목은 없는가 |
| 2 | infra 완료 직후 | architect 컴포넌트 목록 + compliance의 DR·이중화 판정 ↔ infra 사이징 | 모든 컴포넌트가 사이징에 포함됐는가(누락된 컴포넌트 없는가), compliance의 DR·이중화 의무 판정이 infra 설계에 반영됐는가 |
| 3 | session 완료 직후 | architect 컴포넌트 경계 ↔ session 시나리오 | 시나리오가 architect에 없는 컴포넌트를 가정하지 않는가, architect의 "미결 항목"과 시나리오가 모순되지 않는가 |
| 4 | ops 완료 직후 | infra 존 구성 + session 타임아웃 값 ↔ ops 모니터링·정산 전략 | ops 문서가 참조하는 타임아웃·존 이름이 infra·session 문서의 실제 값과 일치하는가 (session↔ops가 SendMessage로 확인했다고 자기보고한 내용이 실제 문서에 반영됐는지 재확인 — 자기보고를 그대로 믿지 않는다). **ops는 infra·session과 병렬이라 비교 상대 문서가 아직 없을 수 있다 — 그 경우 해당 비교 항목만 "보류(비교 상대 미완료)"로 남기고 나머지 항목을 판정한 뒤, 비교 상대가 완료되면 그 항목만 재수행한다** |
| 5 | spec 완료 직후 | session 시나리오 전체 ↔ spec API 목록 | session의 모든 요청-응답 스텝이 spec에 대응 API로 존재하는가 (반대 방향 — spec에만 있고 session에 없는 API도 확인, 스코프 아웃 여부 명시됐는지). **ops의 "테스트 전략"이 언급하는 컴포넌트/API 이름이 이 시점에 확정된 spec과 일치하는지도 함께 확인(6번 체크포인트 3번째 기준의 실제 검증 시점) — spec은 ops와도 병렬이라 spec 완료 시점에 ops 문서가 아직 없을 수 있다. 그 경우 이 항목만 "보류(비교 상대 미완료)"로 남기고 ops 완료 후 재수행한다** |
| 6 (부가) | ops 완료 직후 | ops의 "테스트 전략" 섹션 ↔ 핸드오프 준비도 기준 | 아래 "핸드오프 준비도 기준" 1·2번만 이 시점에 확인(문서 자체의 구체성·도메인 특화 항목 여부는 spec 존재와 무관하다). 3번(spec 이름 일치)은 이 시점엔 spec이 아직 없을 수 있어 검증 불가 — 5번 체크포인트에서 수행. **별도 파일을 만들지 않고 4번 체크포인트와 같은 기록 파일(`04-운영전략.md`)에 이어서 기록한다 — 전체 기록 파일은 5개(1~5번), 6번은 4번 안에 포함** |

## 핸드오프 준비도 기준 ("개발 QA로 넘길 준비가 됐는가")

실제 코드 QA는 못 하지만, ops-designer의 "테스트 전략" 문서가 향후 개발 QA 팀이 그대로 쓸 수 있는 수준인지는 확인할 수 있다. 아래 중 하나라도 미달이면 FIX로 판정해 ops-designer에게 돌려보낸다. **1·2번은 6번 체크포인트(ops 완료 직후)에서, 3번은 spec이 확정된 뒤인 5번 체크포인트에서 확인한다** (ops와 spec은 병렬 관계라 ops 완료 시점에 spec이 아직 없을 수 있다):

1. 각 테스트 항목이 "무엇을 어떤 입력으로 확인하면 어떤 결과가 나와야 정상인가"까지 구체적인가 (예: "penny test"라고만 쓰여 있으면 FIX — "100원 승인 후 즉시 취소, 승인·취소 상태가 정산 배치에 반영되는지 확인"처럼 구체화 필요)
2. 결제 도메인 특화 항목(멱등키 중복 요청, 웹훅 재전송, 타임아웃 후 상태 조회)이 빠짐없이 있는가
3. 테스트 대상 컴포넌트/API가 spec 문서의 실제 이름과 일치하는가 (이름이 다르면 개발 QA 팀이 뭘 테스트하는지 못 찾는다)

## 판정 후 처리

```
매 라운드(FIX/GAP/PASS 무관) → 판정 즉시 {service-root}/_launch-workspace/qa/{NN}-{체크포인트}.md에 라운드 번호·항목별 위치·사유·그 시점의 남은 불일치 항목 수를 이어서 append한다 — 최종 PASS 시점에 한 번만 쓰지 않는다. 이 라운드별 누적 기록이 항목 단위·체크포인트 단위 무진행 판정의 근거(비교 대상)이며, qa 자신이 도중에 재시작되더라도 이 파일을 Read해 이력을 복원할 수 있게 한다(재시작 시 파일이 비어있거나 없으면 이력 없음으로 간주해 처음부터 다시 시작)
완결(PASS/강제 PASS) 후 전제 문서 변경으로 체크포인트가 무효화되어 재수행되는 경우 → 같은 기록 파일에 "⚠️ 재수행 시작 — 이전 사이클 이력과 분리" 구분선을 남기고, 그 이후의 무진행 판정(항목별 사유 이력·체크포인트 최저 기록)은 이 구분선 이후의 라운드만으로 새로 계산한다. 이전 완결 사이클의 최저 기록(예: 잔여 0건으로 끝난 기록)이나 항목 사유 이력을 재수행에 그대로 이월하지 않는다 — 이월하면 재수행에서 나온 정상적인 새 불일치조차 "최저 기록을 갱신 못 함"으로 오판되어 검증 없이 조기 강제 PASS될 수 있다
PASS → 다음 체크포인트로 진행, 위 누적 기록에 최종 판정 표 형식(아래 "팀 밖 단독 트리거 시 출력"과 동일 형식)을 이어서 기록, reporter에게 SendMessage로 결과 요약 전달
FIX  → 생산자에게 SendMessage로 구체적 위치·불일치 내용 전달 → 생산자 수정 → 재검증(항목 단위 무진행 감지 — 그 항목에 이전에 나온 적 없는 새 사유인 한 왕복 횟수 제한 없이 반복)
GAP  → FIX와 동일하게 처리하되, "누락"이므로 생산자가 새로 채워야 할 내용임을 명시
같은 항목에서 그 항목의 재검증 이력 중 이미 나온 적 있는 동일한 위치·동일 사유가 다시 등장(직전 라운드가 아니어도 해당 — 오실레이션 포함)해 무진행 판정 → 그 항목만 강제 PASS 처리 + 생산자에게 SendMessage로 `## 미결 항목(QA 확인 필요)` 섹션을 해당 문서에 추가하도록 요청(QA 자신은 `docs/`에 쓰지 않는다 — QA의 산출물은 `{service-root}/_launch-workspace/qa/`의 판정 기록뿐) + reporter에게 SendMessage로 통지
체크포인트 전체의 남은 불일치 항목 수가 2라운드 연속으로 지금까지의 최저 기록을 갱신하지 못해 무진행 판정(매번 다른 항목이 새로 어긋나 개별 항목은 무진행에 걸리지 않는 경우 대비) → 그 시점까지 남은 모든 불일치를 일괄 강제 PASS 처리 + 동일한 통지 절차
근본적 재설계가 필요한 수준(REDO급) → 판정하지 않고 즉시 리더에게 SendMessage 에스컬레이션, 리더가 팀 전체 영향 범위 판단
"보류(비교 상대 미완료)" 항목이 남아있는 체크포인트 → 그 체크포인트에 대응하는 공유 작업을 `TaskUpdate(status: "completed")`로 아직 마감하지 않는다 — 보류 항목을 재수행해 PASS/FIX/GAP 중 하나로 판정을 완결한 뒤에 마감한다
```
