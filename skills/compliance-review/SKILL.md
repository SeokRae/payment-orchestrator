# Payment Compliance Review — 결제 서비스 규제 준수 검토

결제/PG 서비스가 실제로 부딪히는 규제 5개 도메인을 체크리스트로 대조해, 착수를 막을 수 있는 항목(H급)을 조기에 표면화한다. **법률 자문이 아니다** — 이 스킬의 산출물은 실무 조기 신호 포착용이며, 최종 판단은 반드시 법무/컴플라이언스 검토를 거쳐야 한다.

## 언제 사용하는가

- launch-orchestrator 팀 안에서: `payment-compliance-analyst`가 planner 완료 직후 1회 심층 검토 시, 그리고 이후 팀원의 규제 질의에 응답할 때마다 이 스킬을 호출
- 팀 밖 단독 트리거: 사용자가 특정 서비스·기능에 대해 "규제상 문제없는지", "PG 등록 대상인지", "PCI-DSS 범위가 어떻게 되는지" 등을 물을 때 바로 실행 — 오케스트레이터 전체를 돌릴 필요 없음

## 절차

### 1. 서비스 특성 파악

먼저 아래 질문에 답할 수 있는 정보를 모은다. 이미 제공된 문서(`docs/kickoff/`, `docs/constraints/01-{service-slug}-제약-분석.md`, 사용자 발화)에서 찾되, 없으면 사용자에게 직접 묻는다 — **추정해서 채우지 않는다.**

- 결제 수단이 국내 카드/계좌 기반인가, 해외 카드사/PSP 직접 연동인가?
- 카드번호(PAN)를 자사 서버가 직접 저장/처리/전송하는가, 아니면 결제창을 완전히 위탁(리디렉션/iframe)하는가?
- 정산금을 자사가 직접 수취해 입점업체·파트너사에 재정산하는 구조인가, 단순 정보 중계인가?
- 가상자산·스테이블코인을 취급하는가?
- EU 거주자를 대상으로 서비스하거나 EU 발급 결제수단을 지원하는가?
- 개인정보(카드정보·거래내역 등)를 국외(해외 PSP·해외 클라우드 등)로 이전하는가?

### 2. 해당하는 규제 도메인 선별

`references/regulatory-checklist.md` 말미의 "도메인 선별 가이드" 표로 1번 답변을 대조해, 5개 도메인 중 실제 검토가 필요한 도메인만 추린다.

- 국내 결제 서비스는 도메인 1(전자금융거래법)·도메인 3(개인정보보호법)이 사실상 항상 해당
- PAN을 자사가 만지면 도메인 2(PCI-DSS) 추가, 결제창 완전 위탁이면 SAQ A/A-EP 범위로 좁혀서 검토
- 가상자산·스테이블코인 무관 서비스는 도메인 4를 "해당 없음"으로 명시하고 근거(가상자산 미취급)를 남긴다 — 도메인을 통째로 생략하지 않고 "해당 없음" 판단 자체를 기록한다
- 해외 PSP·카드사 직접 연동이 없으면 도메인 5도 동일하게 "해당 없음"으로 명시

### 3. `references/regulatory-checklist.md` 로드

선별된 도메인 절만 Read한다 (파일 전체가 약 77개 항목이므로 해당 없는 도메인까지 다 읽을 필요는 없음). 각 행의 **항목·트리거 조건·필요 조치·리스크·확인 상태**를 그대로 근거로 삼는다 — 체크리스트에 없는 규제 판단을 새로 만들어내지 않는다.

### 4. 체크리스트 대조

선별된 도메인의 각 행에 대해:
- **트리거 조건**이 이 서비스에 실제로 해당하는지 판정 (해당/비해당/불확실)
- 해당하면 **필요 조치**를 서비스 맥락에 맞게 구체화 (예: "국외이전 근거 확보" → "해외 PSP DPA·SCC 계약 편입 여부 확인")
- 불확실하면 판정을 미루지 않고 "불확실 — {무엇을 확인해야 판정 가능한지}"로 명시

### 5. H/M/L 등급 판정

체크리스트의 **리스크** 열을 기준으로 판정한다 (체크리스트의 "확인 상태"는 리서치 신뢰도이지 등급이 아니다 — 혼동하지 않는다). 일부 행은 리스크 열이 설명 없이 "(표기 없음)"만 있다 — 이 경우 판정을 보류하지 말고, 같은 행의 "필요 조치"를 이행하지 않았을 때의 결과로 등급을 추정하고 근거에 "리스크 서술 없음 — 필요 조치 미이행 기준으로 추정"을 병기한다:

| 등급 | 기준 | 예시 |
|------|------|------|
| **H급** | 미해소 시 형사처벌·영업정지·서비스 강제중단 리스크 | 미등록 PG 영업, VASP 미신고, 정산자금 유용, TPSP 비준수 상태에서 SAQ 스코프 축소 주장 |
| **M급** | 출시 지연·과징금·재작업 비용 발생 | 자본금/인력 요건 미충족, 국외이전 근거 미확보, ISMS-P 인증 지연, SAQ A→A-EP 격상 |
| **L급** | 중장기 로드맵에서 챙기면 되는 항목 | 가맹점수수료율 재산정 주기, 개정법 시행일 대비, DR센터 구축(대형 사업자 한정) |

### 6. 미확인 항목은 법무 확인 요청으로 명시

체크리스트의 확인 상태가 **❓ 미확인** 또는 **⚠️ 부분확인**인 항목은, 등급을 매기더라도 결과 서술에서 반드시 아래 형식을 따른다 — 확인된 사실처럼 단정하지 않는다:

```
{항목명} — {등급} ({부분확인|미확인} — 법무 확인 필요: {구체적으로 무엇을 확인해야 하는지})
```

체크리스트 자체에 없는 새로운 규제 이슈를 질문받으면 "이 체크리스트 범위 밖 — 법무 직접 확인 필요"로 답하고 임의로 추정하지 않는다.

## 출력 형식

### payment-compliance-analyst가 호출한 경우
결과를 등급별 표로 정리해 에이전트에게 반환한다 — 문서 작성(파일 Write)은 호출한 에이전트가 자신의 입력/출력 프로토콜에 따라 수행한다 (`docs/constraints/02-{service-slug}-규제-준수-체크리스트.md`). 이 스킬은 판정 로직과 체크리스트 대조 결과만 제공한다.

### 사용자가 직접 트리거한 경우
아래 형식으로 인라인 응답한다. 대상 서비스가 `{service-root}/docs/`를 이미 갖고 있으면, 결과를 파일로 남길지 사용자에게 확인 후 `docs/constraints/02-{service-slug}-규제-준수-체크리스트.md`에 저장한다(프론트매터는 아래 참조). 그 외(팀 밖 단발성 질문)에는 파일을 만들지 않고 답변만 제공한다.

```markdown
## 규제 준수 검토 결과 — {서비스/기능명}

> 이 검토는 법률 자문이 아니며 실무 조기 신호 포착용이다. 세부 수치·조문 해석·자사 사업모델 해당 여부는 반드시 법무/컴플라이언스 검토로 재확인해야 한다.

### 해당 도메인
- {도메인명}: {해당/비해당 근거 한 줄}

### H급 (즉시 확인 필요)
| 항목 | 필요 조치 | 확인 상태 |
|------|----------|----------|
| ... | ... | ✅/⚠️/❓ |

### M급
(동일 형식)

### L급
(동일 형식)

### 법무 확인 필요 목록
- {❓/⚠️ 표기 항목만 재열거}
```

### 파일로 저장할 때 프론트매터
```yaml
type: literature
project: payment-{service-slug}
created: {YYYY-MM-DD}
tags: [{service-slug}, payment, constraints, compliance, regulatory]
wbs-group: design
wbs-label: "{서비스명} 규제 준수 체크리스트"
```

## 판단 기준

| 상황 | 처리 |
|------|------|
| 서비스 특성이 불명확해 도메인 선별이 안 됨 | 5개 도메인 전부를 가안으로 열거하되 각 도메인에 "해당 여부 미확정 — 서비스 범위 확인 필요" 표기 후 진행 (검토 자체를 중단하지 않음) |
| 체크리스트 항목의 법정 수치가 리서치 시점(2026-08-01) 이후 개정되었을 가능성 | 결과에 "리서치 시점 기준 — 최신 원문(law.go.kr 등) 재확인 권장" 병기 |
| 질문이 5개 도메인 어디에도 속하지 않는 규제 이슈 | "이 체크리스트 범위 밖 — 법무 직접 확인 필요"로 답하고 체크리스트를 억지로 끼워 맞추지 않음 |
| 도메인이 "해당 없음"으로 판정됐으나 서비스 범위가 이후 바뀔 가능성이 있음 | "해당 없음(현재 스코프 기준) — 서비스 범위 변경 시 재검토 필요"로 표기, 판단을 영구적인 것처럼 서술하지 않음 |
