# Payment QA Review — 결제 서비스 설계 문서 정합성 검증

결제 서비스 출시 설계 문서 세트(기획·규제·아키텍처·인프라·세션·운영·스펙)가 개별적으로는 그럴듯해도, **서로 맞물리지 않으면 실제 구현 단계에서 재작업**이 생긴다. 이 스킬은 "문서가 존재하는가"가 아니라 "인접한 두 문서가 실제로 같은 이야기를 하는가"를 확인한다.

## QA의 두 층위 — 반드시 구분한다

| 층위 | 확인 대상 | 이 스킬의 범위 |
|------|----------|--------------|
| **문서 QA** | 설계 문서 A와 B가 서로 정합적인가 (경계면 교차검증) | **범위 안** — 이 스킬의 본체 |
| **개발 QA** | 실제로 짜인 코드가 스펙대로 동작하는가 (테스트 실행) | **범위 밖** — 코드는 별도 코드베이스에 있고, 이 스킬은 설계 문서만 다룬다. 대신 "핸드오프 준비도"(아래 6번)만 확인 |

이 구분을 흐리지 않는다 — "테스트 케이스가 몇 개 있다"는 문서 QA로 확인 가능하지만, "그 테스트가 실제로 통과한다"는 이 스킬로 확인할 수 없는 사실이다.

## 검증 원칙

- **존재 확인이 아니라 교차 비교** — "정산 전략 문서가 있다"가 아니라 "정산 전략 문서가 언급하는 존 구성이 인프라 문서의 실제 존 구성과 같은 이름을 쓰는가"를 확인한다. 두 문서를 동시에 Read해서 구체적 항목 단위로 대조한다
- **PASS / FIX / GAP 3단 판정** — PASS(정합적), FIX(부분 수정으로 해결 가능한 불일치), GAP(한쪽에서 언급조차 안 된 누락). REDO는 없다 — 이미 나온 설계 문서를 통째로 다시 쓸 정도의 불일치는 팀 전체에 영향을 주므로 판정 대신 리더에게 즉시 에스컬레이션한다
- **최대 재작업 2회** — FIX 판정을 생산자에게 돌려보낸 뒤 2회 재검증까지도 같은 불일치가 남으면, 세 번째부터는 강제로 PASS 처리하고 미결 항목으로 리포터에게 넘긴다 (무한 루프 방지)
- **판정 근거는 항상 두 문서의 구체적 위치를 인용** — "정합적이지 않다"가 아니라 "session 문서의 '해외카드 승인' 시나리오 3번째 스텝이 spec 문서 어디에도 API로 없다"처럼 인용 가능한 수준으로 지적한다
- **용어 체계가 달라 비교가 안 되는 경우는 FIX다** — 양쪽 문서에 내용 자체는 있는데 컴포넌트·필드 이름 체계가 서로 달라 대응 여부를 판정할 수 없는 경우, "누락"(GAP)이 아니라 "부분 수정으로 해결 가능한 불일치"(FIX)로 분류한다 — "두 문서 중 어느 쪽 용어로 통일할지"를 생산자에게 SendMessage로 확인

## 검증 매트릭스 (5개 체크포인트)

payment-launch-orchestrator 팀에서는 아래 순서로, 각 생산자가 완료되는 즉시 해당 행을 수행한다. 단독 트리거 시에는 사용자가 지정한 두 문서(또는 전체)에 해당하는 행만 골라 수행한다.

| # | 체크포인트 | 비교 대상 | 확인 기준 |
|---|-----------|----------|----------|
| 1 | architect 완료 직후 | compliance의 H급 규제 항목 ↔ architect 컴포넌트 설계 | H급 규제(예: PAN 비저장 강제)가 실제 컴포넌트 구조에 반영됐는가, 조용히 무시된 항목은 없는가 |
| 2 | infra 완료 직후 | architect 컴포넌트 목록 + compliance의 DR·이중화 판정 ↔ infra 사이징 | 모든 컴포넌트가 사이징에 포함됐는가(누락된 컴포넌트 없는가), compliance의 DR·이중화 의무 판정이 infra 설계에 반영됐는가 |
| 3 | session 완료 직후 | architect 컴포넌트 경계 ↔ session 시나리오 | 시나리오가 architect에 없는 컴포넌트를 가정하지 않는가, architect의 "미결 항목"과 시나리오가 모순되지 않는가 |
| 4 | ops 완료 직후 | infra 존 구성 + session 타임아웃 값 ↔ ops 모니터링·정산 전략 | ops 문서가 참조하는 타임아웃·존 이름이 infra·session 문서의 실제 값과 일치하는가 (session↔ops가 SendMessage로 확인했다고 자기보고한 내용이 실제 문서에 반영됐는지 재확인 — 자기보고를 그대로 믿지 않는다). **ops는 infra·session과 병렬이라 비교 상대 문서가 아직 없을 수 있다 — 그 경우 해당 비교 항목만 "보류(비교 상대 미완료)"로 남기고 나머지 항목을 판정한 뒤, 비교 상대가 완료되면 그 항목만 재수행한다** |
| 5 | spec 완료 직후 | session 시나리오 전체 ↔ spec API 목록 | session의 모든 요청-응답 스텝이 spec에 대응 API로 존재하는가 (반대 방향 — spec에만 있고 session에 없는 API도 확인, 스코프 아웃 여부 명시됐는지). **ops의 "테스트 전략"이 언급하는 컴포넌트/API 이름이 이 시점에 확정된 spec과 일치하는지도 함께 확인(6번 체크포인트 3번째 기준의 실제 검증 시점)** |
| 6 (부가) | ops 완료 직후 | ops의 "테스트 전략" 섹션 ↔ 핸드오프 준비도 기준 | 아래 "핸드오프 준비도 기준" 1·2번만 이 시점에 확인(문서 자체의 구체성·도메인 특화 항목 여부는 spec 존재와 무관하다). 3번(spec 이름 일치)은 이 시점엔 spec이 아직 없을 수 있어 검증 불가 — 5번 체크포인트에서 수행 |

## 핸드오프 준비도 기준 ("개발 QA로 넘길 준비가 됐는가")

실제 코드 QA는 못 하지만, ops-designer의 "테스트 전략" 문서가 향후 개발 QA 팀이 그대로 쓸 수 있는 수준인지는 확인할 수 있다. 아래 중 하나라도 미달이면 FIX로 판정해 ops-designer에게 돌려보낸다. **1·2번은 6번 체크포인트(ops 완료 직후)에서, 3번은 spec이 확정된 뒤인 5번 체크포인트에서 확인한다** (ops와 spec은 병렬 관계라 ops 완료 시점에 spec이 아직 없을 수 있다):

1. 각 테스트 항목이 "무엇을 어떤 입력으로 확인하면 어떤 결과가 나와야 정상인가"까지 구체적인가 (예: "penny test"라고만 쓰여 있으면 FIX — "100원 승인 후 즉시 취소, 승인·취소 상태가 정산 배치에 반영되는지 확인"처럼 구체화 필요)
2. 결제 도메인 특화 항목(멱등키 중복 요청, 웹훅 재전송, 타임아웃 후 상태 조회)이 빠짐없이 있는가
3. 테스트 대상 컴포넌트/API가 spec 문서의 실제 이름과 일치하는가 (이름이 다르면 개발 QA 팀이 뭘 테스트하는지 못 찾는다)

## 판정 후 처리

```
PASS → 다음 체크포인트로 진행, 결과를 _launch-workspace/qa/{NN}-{체크포인트}.md에 1줄 요약 기록
FIX  → 생산자에게 SendMessage로 구체적 위치·불일치 내용 전달 → 생산자 수정 → 재검증(최대 2회)
GAP  → FIX와 동일하게 처리하되, "누락"이므로 생산자가 새로 채워야 할 내용임을 명시
2회 초과 불일치 잔존 → 강제 PASS 처리 + 생산자에게 SendMessage로 `## 미결 항목(QA 확인 필요)` 섹션을 해당 문서에 추가하도록 요청(QA 자신은 docs/에 쓰지 않는다 — 아래 "산출물 저장" 참조) + reporter에게 SendMessage로 통지
근본적 재설계가 필요한 수준(REDO급) → 판정하지 않고 즉시 리더에게 SendMessage 에스컬레이션, 리더가 팀 전체 영향 범위 판단
```

## 팀 밖 단독 트리거 시 출력

```markdown
## QA 검증 결과 — {비교 대상 문서 A} ↔ {문서 B}

### 확인 항목별 판정
| 항목 | 판정 | 근거 |
|------|------|------|
| ... | PASS/FIX/GAP | {문서 A의 구체적 위치} vs {문서 B의 구체적 위치} |

### 개발 QA로 넘길 때 참고
{6번 체크포인트 관련 항목이 있으면 여기 요약, 없으면 생략}
```
